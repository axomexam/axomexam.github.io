# AGENTS.md

Static bilingual (English + Assamese) exam-prep site served from the repository
root by GitHub Pages at https://axomexam.in. There is no build step at deploy
time: the committed `index.html` files are what GitHub Pages serves.

## Web Push notifications — how the pieces fit

The header bell shows the same items as the browser notifications, so there is
one file to edit: `data/notifications.json`.

```
data/notifications.json ──┬─→ bell list  (js/app.src.js fetches it at boot)
                          └─→ broadcast  (tools/send-push.js reads it)
```

- **`js/push.src.js`** — a dwell prompt that appears once a visitor has read
  for `promptDelayMs` (90 s). It closes only through its two buttons; backdrop
  clicks, Escape and a close X are ignored on purpose, so a stray tap cannot
  answer for the visitor. Subscriptions go to Firestore `push_subs`, one
  document per browser, id = `sha256(endpoint)`, with the visitor's `lang` so a
  bilingual item is delivered in the language they read.
- **`sw.js`** — `push`, `notificationclick`, `pushsubscriptionchange`. The
  payload already carries the resolved text, so nothing is fetched at display
  time.
- **`tools/send-push.js`** — reads the feed, lists `push_subs` with a service
  account, sends via `web-push` (VAPID), and deletes rows that return 404/410.
- **`.github/workflows/push-notify.yml`** — the button the owner presses.
  `dry_run` reports the subscriber count without sending.

`push_subs` must allow `create`/`delete` for the public and deny `read`
(an endpoint is enough to push to someone). Reading it is service-account only.

**Rebuild after changing `js/*.src.js`:** `node scripts/minify-assets.js` →
`node scripts/stamp-assets.js` → `node scripts/inject-push.js` →
`node scripts/stamp-assets.js`. `inject-push.js` is idempotent and only adds
the two script tags to pages that lack them; it exists because pages are
generated by many builders and a new site-wide script must reach all of them.
`inject-copy-guard.js` does the same for the copy guard (see the next section).

## Copy guard — question and answer text is not selectable

The owner does not want visitors to copy question/answer text off the page.
Two pieces do that, and they are deliberately separate:

- **`css/style.src.css`** ends with a rule block that sets `user-select: none`
  (and `-webkit-touch-callout: none`, which kills the mobile long-press sheet)
  on `#app` and `#read-modal`. Inputs, textareas, selects and anything marked
  `data-axo-copy-allow` stay selectable, so the header search, the mock-test
  inputs and the Share buttons keep working.
- **`js/copy-guard.src.js`** (minified to `js/copy-guard.js`) cancels the
  gestures CSS cannot: `copy`/`cut`, the context menu outside links,
  `selectstart` and `dragstart`, and shows `.axo-copy-pop` — a centred card
  with a lock badge, a title and one line of text in the page's language.
  It is not the `.toast` pill, which app.js owns.

Only `#app` and the reading modal are guarded; header and footer text is not.

**Contact pages are the one exception.** `/contact/` and `/as/contact/` put
`data-axo-copy-page="allow"` on `<body>`. The CSS block restores
`user-select: text` for that attribute, and `js/copy-guard.src.js` returns
before it registers any handler, so the visitor can copy the support email
address and paste their own message. The attribute is the only supported way
to opt a page out; do not remove the guard tag or the global rules.

The tag reaches every page through `scripts/inject-copy-guard.js`, which is
idempotent and works the same way as `inject-push.js` (pages are produced by
many builders, so the tag is added to the committed HTML). It skips the
leaderboard, which is a separate product. After changing the source:

```bash
node scripts/minify-assets.js
node scripts/inject-copy-guard.js
node scripts/stamp-assets.js
```

This is a deterrent, not a lock: the text stays in the HTML because Google has
to read it, and the same content is still served in plain text from
`/llms-full.txt`, `/feed.xml` and `/data/**/*.json`. Do not weaken the guard
and do not "fix" a page by removing it — the owner asked for it.

### Every new page must carry the guard

The rule applies to **every** page, including pages added later. A new page is
only protected when it does both of these:

1. **Put the content inside `<main id="app">`.** The guard is scoped to `#app`
   and the reading modal, so text in a bare `<main>` or a loose `<div>` is not
   covered, no matter what else the page loads.
2. **Load the script tag** `<script src="/js/copy-guard.js?v=…" defer></script>`
   before `</body>`. The builders do not emit it, so after creating or
   generating pages run:

```bash
node scripts/inject-copy-guard.js   # adds the tag wherever it is missing
node scripts/stamp-assets.js        # fills in the ?v= hash
node scripts/check-copy-guard.js    # must exit 0
```

`inject-copy-guard.js` is idempotent (`Already present` on pages that have it)
and skips the leaderboard product on purpose. `check-copy-guard.js` is the
gate: it exits 1 and lists the pages that are missing the tag, so run it
before every push to `main` and treat a non-zero exit as a stop sign. Fix it
with the two commands above, never by dropping the rule from
`css/style.src.css`.

Also keep the block in `css/style.src.css` last in the file and additive: the
pages load `style.css` directly, so a rule that stops applying silently
re-opens copying on all 3000 pages at once.

## Pushing to `main` — never overwrite anyone's work

This repository is shared and other people push to `main` while an agent is
working. Before every push, confirm the remote tip is an ancestor of `HEAD`;
if it is not, someone pushed in the meantime and the push must be stopped and
rebased instead of forced.

Use the helper, which enforces this and refuses unsafe pushes:

```bash
tools/safe-push.sh origin main
```

It fetches, checks that `origin/main` is reachable from `HEAD` (a pure
fast-forward), and only then pushes. If the remote has commits that `HEAD`
lacks, it prints `BLOCKED` and exits without pushing, so nothing is lost. On
a block, rebase and re-run:

```bash
git rebase origin/main        # resolve conflicts, keep both sides' work
tools/safe-push.sh origin main
```

Never use `git push --force` or `--force-with-lease` to `main`, and never
push directly with `git push` without this check. A manual equivalent of the
guard is:

```bash
git fetch origin main
git merge-base --is-ancestor origin/main HEAD || { echo BLOCKED; exit 1; }
git push origin HEAD:main
```

## Standing rules — do not lose content, do not change the UI

These apply to every change in this repo. They come from the site owner and
they outrank any cleanup, refactor or "nice to have" an agent might want to do.

- **Never lose content.** No sentence, question, answer, note or FAQ item may
  be dropped, shortened or reworded to make a tool's job easier. If a
  generator wants to rewrite a body, diff it against `HEAD` first and revert
  anything that is not the change you were asked to make.
- **Never change the UI.** Markup, CSS classes, layout, spacing and the
  client-side render path stay as they are. A content or SEO fix must be
  invisible to a reader looking at the page.
- **Exception, owner-requested (Nov 2026): the "Book details" card on the exam
  book pages.** Every `exams/<id>/index.html` and its `/as/` twin carries one
  `[data-axo-book-details]` card at the top of the book — under the hero,
  above the subject cards. It is a library record: publisher, per-book code,
  edition, language, exam, recruiting body, subject / chapter / question
  counts, format, and the published and last-updated dates. It is the one
  visible block added on the owner's request, so do not strip it as UI churn.
  Two halves must stay in step:
  - `js/app.src.js` → `bookDetailsFactsHTML()` fills the facts,
    `examBookDetailsHTML()` places them in the hero's right column (the
    cover's neighbour, under the description) and `hydrateExamBookDetails()`
    fills the counts asynchronously. Below 640px the column is hidden and
    `examBookDetailsButtonHTML()` shows a "More details" button that opens the
    same facts in a bottom sheet (`openBookDetailsModal()`, close button plus
    backdrop and Escape). The two breakpoint rules are injected once by
    `ensureBookDetailsStyle()`; do not move them into `css/style.css` — the
    static pages must keep the facts visible without JS;
  - `tools/add-book-details.js` writes the same markup as the static crawler
    copy inside the hero (or `.page-head` on a page built without a cover),
    which the runtime replaces on load. It only touches the books listed in
    `EXAM_BOOKS_READY` and strips the block from the rest, so a "coming soon"
    page never advertises a record. Re-run it after rebuilding a book page; it
    is idempotent (`Changed: 0` on a clean tree).
  Every fact lives in `data/exams/index.json` → `exam.book` (code, authority,
  `authorityUrl` — only for portals already listed in `data/sources.json` —
  and the published / updated dates). Subject and chapter counts are the leaf
  nodes of that exam's section tree, and the question count is
  `data/counts.json` → `examSectionCounts`, the same manifest the hero prints,
  so the card can never disagree with the page. Labels are the `book.*` keys
  in `js/i18n.src.js`; rebuild with `node scripts/minify-assets.js` and
  `node scripts/stamp-assets.js` after editing either half.
- **Every page opens with exactly one `<!DOCTYPE html>` / `<html lang="…">`.**
  The exam-book builders borrow another book's page as "chrome": they copy its
  head and re-emit the doctype themselves. `chrome()` in
  `tools/lib/exam-book-pages.js` and `tools/build-adre-grade-3.js` must
  therefore slice the borrowed head from `<head>`, **not** from byte 0 — taking
  the whole prefix duplicated the doctype and `<html>` line once per book that
  borrowed a leaf from another book (RRB NTPC reached three). If a page ever
  shows a repeated leading doctype, fix the slice and run
  `node tools/fix-duplicate-doctype.js` (idempotent) to repair the tree; it
  keeps the first `<html lang>` so the `/as/` twins stay `lang="as"`.
- **No ad code on the Assamese (`/as/`) pages.** Assamese is not a supported
  AdSense language, and Google's publisher policies forbid ad code on a page
  whose content is primarily in an unsupported language. The `/as/` twin must
  carry **no** AdSense trace, not just the loader: the
  `google-adsense-account` ownership meta, the `pagead2.googlesyndication.com`
  `dns-prefetch`, the `<!-- Google AdSense Script -->` comment, the
  `adsbygoogle.js` loader, and the `ins.adsbygoogle` / `.google-auto-placed`
  rules inside `<style id="axo-layout-reserve">` all come off. The `.main-nav`
  rules in that same style block are **not** ads (they reserve the JS-built
  desktop nav) and stay, so the Assamese page keeps its twin's layout-shift
  behaviour. `tools/lib/strip-adsense.js` is the single source of truth for
  this; `tools/build-as-twins.js` calls it on every rebuild, so a twin can
  never re-acquire the footprint, and `scripts/inject-adsense-meta.js` skips
  `/as/`. To clean the committed tree after changing the rule, run
  `node tools/strip-adsense-from-as.js` (idempotent; a clean tree reports
  `changed: 0`). Only indexable English content pages carry the loader. The
  Google Analytics tag (below) is a separate thing and **does** go on every
  page, `/as/` included.
- **Every published page carries the Google Analytics tag — `/as/` too.**
  The site's GA4 measurement ID is `G-PBPXK2Q799`, in the `gtag.js` snippet
  at the top of `<head>` (marker `googletagmanager.com/gtag/js`). This is
  **analytics, not ads**, so unlike the AdSense loader it belongs on the
  Assamese pages as well. A new page (any book, any language) is not done
  until it carries the tag: `node scripts/inject-ga.js .` injects it into
  every HTML file that lacks it and is idempotent (re-running reports
  `Injected: 0`). The only pages that legitimately lack it are the "This page
  has moved" redirect stubs, and even those should carry it so a redirect hit
  is still counted. After adding pages, run the injector and confirm
  `Injected: 0` / `Already present` equals the file count.
- **Every page gets its own accurate, topic-wise SEO head.** Title,
  description, canonical, hreflang and JSON-LD must describe *that* page's
  actual topic, in the reader's language, with no clamping (`…`), no template
  filler and no duplicate across pages. `tools/seo-audit.js` must stay at
  `dup titles: 0`, `dup descriptions: 0`, `title >60 chars: 0` and
  `desc >160 chars: 0`.
- **All content must be readable by Googlebot with JavaScript off.** The
  crawler copy is the static block *outside* `<main id="app">`; do not move it
  inside `<main>` and do not hide it behind JS. Verify with a Googlebot user
  agent that the URL returns 200, is not `noindex`, and has real words.
- **No broken hreflang.** Every `hreflang="as"` target must exist, and the
  pair must be reciprocal. `tools/seo-audit.js` reports a miss as
  `sitemap alt miss`; it must stay at 0.
- **Answer keys must stay random.** In every MCQ bank the correct option must
  be spread over A/B/C/D — never a run of one slot and never all answers in the
  same position. A new bank is authored with the answer wherever it belongs,
  then the options are shuffled so the key is balanced; the option that was
  correct stays the same option, only its position changes. Check with
  `node tools/balance-answer-keys.js --book <book> --topic <topic> --check`,
  which must report 0 skewed topics (no slot holding >=50% of a topic's keys).
- **Deduplicate by meaning, not just exact text — and never repeat wording.**
  The same fact is often needed in more than one book: an exam-specific bank
  (say RRB NTPC) and a state or general-knowledge bank may both legitimately
  need "the capital of Assam" or "the first oil well in Asia". Having that fact
  in two books is allowed — but writing it the same way twice is not, because
  the site then carries duplicate content. So whenever a question is reused
  across books, reword (ghuma-phirake) the stem, the options and the
  explanation so each instance reads differently; a reader must never meet two
  identical questions. An exact string match is not enough to check this: the
  repo already holds ~95k stems and explanations, so the same fact is often
  asked with slightly different wording (e.g. a new "In which year was the Food
  Corporation of India established?" against an existing "In which year was the
  Food Corporation of India (FCI) established?"). Before committing a bank, run
  a fuzzy check of every new stem and explanation (English and Assamese, case-
  and punctuation-folded) against all other question text in `data/` —
  `difflib.SequenceMatcher` with a ~0.90 ratio is a good threshold — and reword
  every hit until the count is 0. Do not drop a fact that a book genuinely
  needs; phrase it differently instead. This is a standing rule: do not
  re-introduce near-duplicate stems or explanations in any future bank.
- **Every question-answer page also carries its own 1300+ word study
  article.** A page that publishes an MCQ bank is not "done" when the
  questions are in. It must also carry a topic-relevant long-form article
  panel — an `h2`, overview prose, a key-facts list and a short FAQ — in
  **both** English and Assamese, and **each** language must reach **1300
  words minimum**. The article is written for that topic (exam-relevant,
  high-quality, covering the syllabus around the questions — not template
  filler and not a restatement of the MCQs), and it must not reuse another
  page's prose. This is a standing rule: it applies to **any new
  question-answer page in any book**, not only RRB NTPC.
  - RRB NTPC source files: `tools/rrb-ntpc-ga-articles/<group>/<leaf>.js`,
    each exporting `{ h2, p: { en, as }, list: { en, as }, faqs }`.
  - Render with `node tools/rrb-ntpc.ga-extra.js`; gate with
    `node tools/rrb-ntpc.ga-extra-check.js`, which must end
    `articles failing the 1300-word floor (either language): 0; missing: 0`.
  - The panel lives in the `axo-extra-content` block placed **after
    `</main>`** (outside `<main id="app">`) so Googlebot reads it with JS
    off, and `tools/build-as-twins.js` copies it into the `/as/` twin.
- **Maths and Reasoning banks must cover *every type* of a topic — never one
  type repeated to reach a count.** When any Maths or Reasoning book, mock
  test, exam bank or topic page is authored, each topic it contains must
  exercise **all the question types that topic has**, not one type (or a
  couple) repeated until the target number of questions is reached. Take
  Number System: its types include basic terms, divisibility rules, place
  value and face value, unit digit and cyclicity, remainders, factors and
  multiples, number of zeros, and so on — a Number System set that only asks
  "is X prime", or only HCF/LCM, is **not** done however many questions it
  holds, because it leaves most of the topic's types untested. The same
  applies to **every** Maths topic (percentage, ratio and proportion,
  average, time-speed-distance, time and work, profit and loss,
  simple/compound interest, mixture and alligation, algebra, geometry,
  mensuration, trigonometry, …) and **every** Reasoning topic (number and
  alphabet series, coding-decoding, blood relations, direction and distance,
  order and ranking, syllogism, clock and calendar, non-verbal reasoning, …).
  - **How to author a topic:** first enumerate that topic's types from its own
    syllabus — the `h3` sub-sections on the topic page (e.g.
    `topic/math/arithmetic/number-system/index.html`) and the topic's
    deep-article in `data/deep-articles/` — then make sure the bank carries
    questions for **each** listed type, spread evenly and without leaning on a
    single type.
  - **The requested count is a floor, not a licence.** A target like "20
    questions" sets the minimum total, not permission to fill all 20 with one
    type. If the count is too small to cover every type, cover every type
    anyway and raise the count.
  - **Where this bites:** the exam banks
    (`data/exams/<exam>/<subject>/<topic>/question-NNN.json`), the subject mock
    tests (`data/mock-test/<subject>/<group>/set-N.json`), the exam mock sets
    (`data/exam-mock-sets/…`) and the `topic/math/**` / `topic/reasoning/**`
    pages. This is a standing rule for any future Maths or Reasoning bank in
    any book, in both English and Assamese.
- **Non-Verbal Reasoning keeps the existing figure format — only the shapes
  and images change.** Every Non-Verbal Reasoning question (figure series,
  figure analogy, figure classification, figure matrix, mirror image, water
  image, embedded figures, counting figures, pattern completion, paper folding
  and cutting, rule detection, shape construction and grouping, cube and dice)
  must be authored and rendered in **exactly the format already used on the
  Assam Police Non-Verbal Reasoning pages** — the same markup, classes and
  render path — with **each question carrying its own distinct shapes and
  images**, never a copied or repeated figure. The reference is
  <https://axomexam.in/exams/assam-police/logical-reasoning/non-verbal-reasoning>
  and its leaf pages (e.g. `…/non-verbal-reasoning/figure-series/`); copy that
  shape, not the content.
  - **Question figure** goes in the item's `fig` field and renders inside
    `<div class="nv-media">…</div>` (the prompt diagram: the series, matrix or
    pattern to be read).
  - **Answer options are picture choices**, each an object
    `{ option: "A"|"B"|"C"|"D", fig: "<svg…>" }` (an optional `text` caption is
    allowed). They render as a labelled grid
    `<div class="nv-fig-grid">` → `<div class="nv-fig-item">` →
    `<div class="nv-fig-key">(A)</div>` → `<div class="nv-fig-box">…</div>`,
    with `.nv-fig-grid-compact` used inside the MCQ card. Do **not** fall back
    to text-only options for a non-verbal question — that is not the format.
  - **Figures are inline SVG** (`<svg viewBox=…>` with `polygon`, `line`,
    `rect`, `circle`, `path` shapes), stroke `#334155`, no external image
    files and no `<img>` URLs. An optional data table uses the `table` field
    and the `nv-table-wrap` / `nv-table` classes.
  - **Source of truth:** the question JSON lives in
    `data/content/reasoning/<topic>.json` (`q: { en, as }`, `fig`, `options`,
    `correct`, `explanation: { en, as }`) and is rendered by `js/app.src.js`
    (`mediaBlock`, `figureOptions`, `figureOptionsHTML`) into `js/app.js`,
    styled by `css/style.src.css` → `css/style.css` (the `nv-*` rules). Change
    the content, not the format.
  - **Every question must show different shapes/images.** Two questions in the
    same bank (and across the site) must not reuse the same figure set; each
    prompt figure and each option figure is drawn for that question's own
    pattern, so a reader never meets the same picture twice. The figures must
    also actually match the question and its correct answer, and the question
    text and options stay bilingual (English and Assamese) like every other
    question.
- **Verify before shipping.** Run `node tools/seo-audit.js` and confirm
  `thin (<300w): 0`, `missing H1/desc/canonical/JSON-LD: 0`, and the duplicate

- **Keep internal files out of the published site.** `.nojekyll` (repo root)

## Gotcha: `.nojekyll` is load-bearing — do not remove it

The repo serves from `main:/` with GitHub Pages in **legacy** build mode. With
no `.nojekyll`, GitHub runs Jekyll over the repo, and Jekyll turns every root
`*.md` into a published, indexable page rendered in its own theme:

| URL | What it was |
| --- | --- |
| `/AGENTS.html` | this handbook, ~11k words, indexable, no `robots` meta |
| `/SEO-AUDIT.html`, `/SEO-ACTION-PLAN.html` | the internal SEO notes |
| `/AGENTS.md`, `/SEO-*.md` | the raw markdown, served as `text/markdown` |

Jekyll also served its theme CSS at `/assets/css/style.css` (never in the
repo), so those pages looked like part of the site. Search and the AdSense
review saw a large off-topic page wearing the site's own theme, next to the
keyword research in `keyword-map.csv`.

`.nojekyll` at the repo root switches Jekyll off, so only committed files are
served and no `*.md` becomes a page. Nothing else changed: every real page's
bytes were identical before and after (md5 compared), and the only other
casualty is `/assets/css/style.css`, which nothing in the repo links.

Do not "clean up" `.nojekyll` as an empty file — it is the switch.

## Gotcha: a named `User-agent` group replaces the `*` group

`robots.txt` lists 32 named crawlers (Googlebot, Mediapartners-Google, GPTBot,
Bingbot, …). In robots.txt a group that names a user-agent **replaces** the
`*` group for that crawler — it does not merge with it. While the named groups
carried only `Allow: /`, the `Disallow: /dist/` on the `*` group never applied
to Googlebot or to any named crawler, and the same would have been true of
every internal-path `Disallow` added later.

The file therefore repeats the full `Disallow` list inside the named group.
Change **both** groups together, then check the result against the matching
rules (longest matching path wins; `Allow` wins a tie) for Googlebot,
Mediapartners-Google and `*` before pushing.

`/data/` must stay crawlable and is not blocked: the SPA fetches
`/data/mock-test/*.json` at runtime and the previous-year pages link
`/data/**/*.pdf`.

- The original 80 items stay in `tools/legacy-banks/.../assam-history/` and are
  sorted into the three leaves by the `assam-history` rules added to `RULES` in
  `tools/build-dhs-dme-technical.js`, which read the stem. The fallback is the
  last leaf in the `LEGACY_BANKS` entry, so a new rule must cover any stem that
  would otherwise fall through to `assam-history-modern`.
- The 248 new items are authored as row arrays in
  `tools/assam-history-src/{ancient,medieval,modern}-part*.json` and generated
  into `tools/dhs-dme-technical.assam-history-extra.js` by
  `tools/gen-dhs-assam-history.js`. Each generated item carries an explicit
  `leaf`, which `classify()` honours before any regex runs. That is deliberate:
  Assam History vocabulary overlaps badly across periods (a "Koch" stem can be
  medieval politics or modern land policy), so a stem regex cannot be trusted
  for authored bulk content.

Row format is nine fields —
`[qEn, qAs, [o1En,o1As], [o2En,o2As], [o3En,o3As], [o4En,o4As], correct, exEn, exAs]`
— where `correct` indexes the option order as written. The generator rotates
options by the item's **position inside its leaf** (`i % 4`), not by a global
sequence number. A global counter produced an almost constant shift within a
leaf and pushed 98 of 114 ancient keys onto option B; the per-leaf index gives
an even spread.

**Geography** (`general-knowledge/geography`) was one flat leaf of 80 items
and is now two leaves:

| leaf | items |
|---|---|
| `assam-geography` | 304 |
| `india-geography` | 392 |

Same two mechanisms as Assam History, with one twist that matters: the India
rule is `/.*/` and `india-geography` is the fallback leaf, so the India regex
matches everything and only the Assam rule actually decides. That is
deliberate — a stem that misses every Assam keyword lands in India rather than
being dropped, and a new Assam keyword must be added to the Assam rule, not to
the India one.

**The 80 legacy items had every answer key on option A** (41 of 80). Merging
them as-is skewed both new leaves badly. They were rotated by position before
the merge, which is now the pattern: check the legacy bank's key spread
whenever an old flat bank is split.


Merging generated items into the legacy bank must be idempotent — filter out
every id containing `-extra-` before appending, or a second run doubles the
bank.

**A shared stem template is the real duplicate risk, not identical wording.**
Ten items had to be reworded at 796 scale even though only one was an exact
repeat. Seven opened with the same eight words as another item ("The ancient
Kamarupa kings' grants show that the state …", "The Ahom kingdom's main reason
for …"), which reads as the same question to a candidate and would fail any
similarity check. Two more had a common opening that made different answers
look like a contradiction. Audit at both eight and ten word prefixes, not just
on exact matches — exact matching missed all of them.

Verified at 796: zero duplicate stems at eight and ten word prefixes, zero
duplicate options inside any item, zero bilingual gaps, every item with four
bilingual options and a bilingual explanation. Keys are balanced per leaf
(ancient 63/61/64/62, medieval 74/69/73/73, modern 67/65/61/64) because the
generator rotates by position inside the leaf.

**Assamese text must not carry English words.** Two leaked in ("pilots",

## Session record — Nov 2026 RRB NTPC content-load fix (consolidate question files)

**Symptom.** RRB NTPC topic pages sometimes rendered with no questions.

**Root cause.** RRB NTPC was the only book stored as **one file per question**
(`question-001.json` … `question-430.json`). Every other book uses the
"one topic = one file" layout (`PRIMARY = "question-001.json"`). Two effects:

1. A single topic page fetched 300–430 files at runtime (biology = 311 requests,
   modern-history = 431).
2. `listExamQuestions()` asked the **GitHub Contents API first**, which is rate
   limited to **60 requests/hour** for anonymous callers. After a couple of page
   views it returned `403`, the loader fell through with `questions=[]`, and the
   page rendered blank.

**Fix.**
1. New tool `tools/consolidate-exam-question-files.js` merges each multi-file
   topic into `question-001.json`, deletes the redundant files and rewrites
   `index.json`'s `files` array. Question order is preserved, so the rendered
   pages are unchanged (verified byte-identical against the 23 previous
   multi-file topics). Result: 23 RRB topics merged, 6,328 files removed, 6,351
   questions kept (assam-police was deliberately left on its original layout,
   since it was not affected by the load issue).
2. `js/api.src.js` now prefers the folder's `index.json` manifest (one
   same-origin request). The GitHub Contents API stays as the fallback, and is
   still used first when `CONFIG.USE_REMOTE` is on.
3. `tools/build-rrb-ntpc.js` gained a `readBankSize(rel)` guard: the seeder never
   shrinks a bank that has grown past its seed sample, so re-running it cannot
   wipe the real questions.

A topic now loads in 2 requests (manifest + one bank) instead of 311.

**Rule going forward — one topic, one file.** Do not add `question-002.json`,
`question-003.json`, … to any topic. Append to the topic's existing
`question-001.json` and make sure `index.json`'s `files` array still lists it.
If a topic ever has more than one `question-*.json`, run
`node tools/consolidate-exam-question-files.js --book <id>` (add `--check` to
report without writing).

--book=<slug>` renders the `axo-hub-guide` panel above the topic cards on every hub
page of that book, using `tools/<slug>.hub-guides.js` (SECTION / GROUP / ROOT; set
`counts: false` on an entry whose intro already states the topic and question counts).
Rerun it after topic counts or card lists change; it replaces the block instead of
duplicating it. Book root pages take the book-wide totals from the rendered pages, so
the numbers in the guide cannot drift from the hero.

**Generated maths needs an answer-key audit.** `tools/gen-alg-quadratic.py` builds
quadratic items from `(a, b, c, r1, r2)` tuples; two tuples shipped roots that do
not solve their own equation (`2x²-7x+3` marked 1 and 3; `2x²-9x+4` marked 1 and 4).

reports six "missing" twins. They are not missing; check the `verbal-reasoning`
path before treating it as a defect.

**Gotcha — `build-as-twins.js` is not idempotent against committed pages.**
Pages that are `noindex` are deliberately left out of `twinSet`, so their
`/as/` twin links are not rewritten. Re-running the twin builder over an
already-committed tree therefore reports ~1,200 "changed" pages that are just
that difference. If a fix does not change page markup, do **not** re-run the
twin/keyword/SEO chain to "refresh" it — revert `*.html` and only re-run
`scripts/stamp-assets.js` so the `api.js?v=` hash matches the rebuilt bundle.

**Gotcha — `--only` breaks `/as/` link prefixes.** `rewriteInternalLinks` only
points a link at `/as/...` when the target page is in `twinSet`, and `--only`
narrows `twinSet` to the single page being rebuilt. Every nav, breadcrumb and
sibling link on that twin then stays on the English URL, so an Assamese reader
is dropped back into English on the first click. The page still looks right and
passes every audit (canonical, hreflang and word count are unaffected), so this
only shows up if you actually click a link. To build one twin correctly, run
the full builder in a scratch copy and take only the new files:

```bash
tar -c --exclude=.git . | tar -x -C /tmp/gen && cd /tmp/gen
node tools/build-as-twins.js
# copy just the target directory back; leave the ~1,290 drifted pages alone
cp -a /tmp/gen/as/<path>/. as/<path>/
```

`--prefix <dir>` has the same flaw when the prefix is narrower than the link
targets on those pages. Verify with
`grep -c 'href="/as/' as/<path>/index.html` — it must be non-zero.

`rewriteInternalLinks` now also points a link at `/as/...` when that Assamese
file already exists on disk, so a narrow `--only`/`--prefix` run no longer
sends the nav back to English; the target page only has to exist.

**Structured data runs in a fixed order.**

```bash
node tools/latest-schema.js      # English graph
node tools/build-as-twins.js     # /as/ copy: URLs, inLanguage, text
node tools/apply-real-dates.js   # dates last, from git history
```

The Assamese graph is a copy of the English one, so a schema pass that rebuilds
`/as/` graphs from page metadata throws away every node it does not itself
produce: Quiz and the questions under it vanished from all 330 Assamese topic
pages that way. `latest-schema.js` now leaves `/as/` graphs alone, correcting
only a stale author `@id`, and adds the editorial-team definition when a
generator page points at it without defining it.

The date pass is what makes `build-as-twins.js --check` report drift: it
rewrites the twin's dates into Assamese month names, which the builder's raw
output does not contain. Compare before the date pass, not after.

**Caveat 1 — this is a single-page app.** `bindLinkInterception` in
`js/app.src.js` swallows every internal `<a href="/...">` click and calls
`navigateTo()`, which is `history.pushState` + re-render. `/topic/` links are
exempted and do a real page load. GA4's Enhanced Measurement sends a
`page_view` on `pushState`, `popState` and `replaceState` by default, which is
what makes the SPA measurable at all. If that option is ever switched off in
the property's Enhanced Measurement settings, every internal navigation
disappears from the reports while the landing page view stays — the traffic
would look like a fraction of reality. Worth confirming in the GA property
before trusting the numbers.

**Caveat 2 — GA is client-side, so it undercounts.** Ad blockers and
privacy-focused browsers drop the tag silently, and on a mobile-first Assam
audience that is not a small share. There are no server-side logs to compare
against, because GitHub Pages does not expose them. GA is the only view of
traffic this site has, and it will always read lower than reality.

**Deep-link quirk.** A path with no static file (for example
`/topic/gk/assam-history`) is served `404.html`, which redirects to
`/?/<path>`, and the app then `replaceState`s the clean URL back. The first
page_view therefore lands on `/` with a `?/` query before the cleaned URL is
recorded, so a deep-linked visit can be attributed to the home page. The
trailing-slash URLs (`/leaderboard/`) serve 200 directly and are unaffected.

### Leaderboard name validation hardened against junk input (17 Nov 2026)

**Problem.** The owner reported visitors submitting "ulta-pulta" names — random
keyboard mashing and placeholder words. `validateName` only enforced 2–20
characters, an allowed-character class, and a profanity substring list, so
`asdfgh`, `qwerty`, `1234`, `test`, `aaaa`, `hello`, `admin` and `abcd` all
reached the public board.

**Fix.** `validateName` in `js/leaderboard.src.js` gained four new checks and
two new rejection codes:

- `noname` — no letter at all after stripping digits, spaces and underscores
  (`1234`, `1 2 3`, `___`). The letter test uses `\p{L}\p{M}`, so an Assamese
  or Devanagari name still passes; a Latin-only `[a-z]` test would have
  rejected `ৰাহুল`.
- `junk` — covers three shapes: a whole-word match against `JUNK_NAMES`
  (`test`, `admin`, `hello`, `abcd`, …), a single repeated character (`aaaa`,
  `zzzz`), a four-character run along a keyboard row or the alphabet in either
  direction (`asdf`, `qwerty`, `fdsa`, `4321`), and five consonants in a row
  (`zxcvbn`).

`JUNK_NAMES` is matched against the flattened name with digits removed, so
`Test`, `test_1` and `TEST 12` all land in one bucket. Two entries were
deliberately left out: `nan` and `nil` are real names in India, and blocking
them would cost more than the junk they filter.

The mash checks run on `flat`, the ASCII-only projection of the name. For an
Assamese or Devanagari name `flat` is empty, so they are skipped rather than
misfiring — that is why the guard is `if (word)` and not an unconditional
chain.

**Messages.** `lb.name.junk` and `lb.name.noname` were added to both `en` and
`as` dictionaries in `js/i18n.src.js` and mapped in the modal's error switch
in `js/leaderboard-ui.src.js`. Dictionary parity is unchanged at 388 keys per
language.

**Verified end to end against the real minified bundles.** Driving the actual
opt-in popup and name modal in jsdom: 13 junk inputs blocked with the right
message, 8 real names saved (including `ৰাহুল`, `अनुज`, `Rahul Das 21`,
`Amit_Kumar`), and the Assamese UI renders the Assamese strings. Unit coverage
lives in the `lbname` suite (76 cases).

**Known limit.** A dot or other punctuation is still rejected, because the
security rules' character class excludes it; `B. K. Sharma` cannot be entered.
That predates this change.

`tools/nv_geom.py` counts lines, triangles, rectangles and squares exactly
from a list of drawn segments. It computes every intersection, treats a side
as drawn when the whole span is covered by collinear segments (grid lines are
drawn cell by cell), and then counts 3-cliques for triangles and 4-point
rectangles/squares. Every published counting answer is that exact number, so
never hand-write a count in this topic.

Authoring rules learned here:

- Use integer coordinates only. Regular polygons (pentagon, hexagon) and
  thirds of 80 give rounding drift and the counter then misses real shapes.
- In a pattern matrix, a square must be drawn axis-aligned: `S.regular(4)`
  starts at -90 degrees and renders a diamond, which reads as a different
  shape in a side-counting rule.
- For "two views of the same die", exactly five numbers may be visible; if a
  neighbour repeats across views the opposite face is not determined.
- Distractor shapes must be verified absent with the same counter, otherwise
  a sharp student can defend two options.

"count every triangle whose sides are drawn" convention and were corrected:

## Repeated inline styles become .qsN classes

The generators emit spacing as inline style attributes, and the same twenty-odd
strings repeat millions of times ("margin:2px 0;" alone appears 710,000 times).
`tools/derive-style-classes.js` copies those declarations into `.qsN` classes at
the end of `css/style.src.css`, and `tools/move-inline-styles.js` swaps the
attribute for the class name. Declarations are copied unchanged, so nothing
moves on the page.

Two details matter if you touch either script:

- The classes carry `!important`. An inline attribute outranked every rule in
  the stylesheet; without the marker a selector one compound deeper
  (`.info-panel ul`) starts winning and spacing shifts. The block also sits last
  in the file, so ties break the way they did before.
- Class names must never be reassigned. A page already points at `qs14`, so the
  derive script keeps existing entries and only appends new patterns. If the
  mapping is ever lost, rebuild it from the previous commit rather than rescanning
  the working tree, which no longer holds the inline attributes:
  `git worktree add /tmp/head-site HEAD && node tools/derive-style-classes.js --root=/tmp/head-site`

Order after a content pass that writes new markup:
`derive-style-classes.js` → `move-inline-styles.js` → `minify-assets.js` →
`stamp-assets.js`.

The static question blocks are not what visitors see: `js/app.js` renders its own
cards into `#qa-list`, and the static copy exists for crawlers and no-JS readers.
That means a spacing regression here would be invisible in a browser, so verify
it where it does show. Render both versions with scripts off and compare computed
styles element by element; a 12,000-element page and its Assamese twin are the
useful test pair.

## Explanations are the product; measure them

`node tools/check-explanations.js` audits every multiple-choice item in `data/`
and reports three things a reader notices immediately:

- **length** — 25+ words in English, 20+ in Assamese;
- **elimination** — the explanation names at least one wrong option, or says why
  the others fail. Without it the explanation only restates the key;
- **restatement** — at least 6 content words that the question did not already
  contain (judged only on explanations that pass the length floor, because a
  12-word explanation always looks like a restatement).

Baseline on 2026-11-25: 68,138 distinct MCQs, 4% pass all three, 93% are under
25 words, median 12. The bank is an answer key with a teaching layer promised in
the copy. Items in `data/content/*` shaped `{q, a}` are study notes, not MCQs,
and the tool skips them.

`--json <path>` exports one row per question for batch work, `--area <prefix>`
narrows to a directory, `--strict` exits 1 while anything fails. Rewriting is
subject work, not a script: the explanation has to say something true that the
question did not.

### Repairing options, not just explanations

An item whose three distractors are unrelated words tests nothing:
`Choose the synonym of 'beautiful' → absurd, lovely, abrupt, abundance`. 298 of
the 438 synonym items are in that state. `tools/set-source-options.js` replaces
the whole option set and the explanation together, because they must agree.

Two traps, both hit once:

- **The answer is named, not indexed.** `"correct": "sudden"`, never `3`. The
  source row, the generated JSON and the page hold the options in three
  different orders, so a positional replacement silently moves the answer key.
  After writing, the tool re-anchors `correct` to the index of the named word.
- **Distractors pair by position within the distractor list**, excluding the
  answer word, because that list order does survive the shuffle.

Verify a batch, never trust it: for every row, the generated JSON's
`options[correct]` must equal the named answer, and the page's
`Answer:</strong> <span>X) word</span>` letter must point at that same word.

## AdSense state and the quality bar (Nov 2026)

AdSense rejected axomexam.in for **"low-value content"**. Re-review opens
**1 Dec 2026**. Until it passes, page count, traffic and markup are not the
goal — question quality is. What that means in practice:

- Four real options per question, all distinct, and every distracter must
  belong to the question it sits under. No shared filler pool (`Elephant`,
  `Camera`, `Village`, `boxing`, `east`) reused across unrelated questions.
- The correct answer must be checkable against a source, and the explanation
  must say why the others are wrong. Explanations under 25 words read thin to
  a human reviewer; treat that as a defect, not a style choice.
- Never invent a fact, a date, a name or a source to fill a gap.
- The option audit is `node tools/check-options.js`; it prints counts per
  bank plus a sample. Run it after any bank repair and compare the totals.

A question lives in three places and all three must move together, or the
page and the data disagree:

| layer | file |
|---|---|
| source bank | `tools/english-src/<bank>.js` |
| question data | `data/exams/<exam>/<section>/question-001.json` |
| rendered page | `exams/<exam>/<section>/index.html` |

`tools/set-source-options.js` rewrites the source row, then the JSON, then the
option spans inside the `qa-item` blocks of the page — it never touches
anything outside those blocks. Mock sets are a fourth copy: `data/exam-mock-sets/`
is drawn from the exam banks by `tools/build-exam-mock-sets.js`, so a bank
repair leaves the sets stale until that builder is re-run.

## Merging a working branch into `main`

`main` moves while a branch is open. Fetch first. If `origin/main` is not an
ancestor of the branch, **merge it in** — do not force anything, and do not
resolve by taking the branch wholesale.

Conflict rule, learned the hard way (Nov 2026, 209 conflicts):

- **`<title>`, `og:title`, `twitter:title`, `meta description`, `canonical`,
  `<h1>` always come from `main`.** Those lines are the owner's tuning work;
  a branch built weeks earlier holds the older wording.
- Everything else — body markup, classes, question blocks, translations —
  comes from the branch.
- Before deciding, check who actually touched the file:
  `git log --oneline main..origin/main -- <file>`. No commits there means
  `main` has no opinion and the branch version stays.
- Minified files (`css/style.css`, `js/i18n.js`) conflict as one giant line.
  Merge them at token level (rules split on `}`, i18n keys split on `",`) and
  verify both sides' additions survive; the owner's CSS rules and the branch's
  new classes must both be in the result.
- After any CSS/JS merge: `node scripts/stamp-assets.js`, then
  `node scripts/stamp-assets.js --check` must print `Drift: 0 file(s)`.
  A stale `?v=` hash plus new class-based markup serves a cached old stylesheet
  and the layout breaks for returning visitors.

Verification that must pass before pushing a merge (numbers from the Nov 2026
merge, which is the shape of a healthy tree):

| check | expected |
|---|---|
| title / canonical / h1 overridden, on files `main` touched | 0 / 0 / 0 |
| pages | 3,225 |
| sitemap URLs that resolve to a file | all of them |
| pages outside the sitemap | only `noindex` aliases |
| duplicate titles | 0 |
| indexable pages without an `<h1>` | 0 |
| broken or non-reciprocal `hreflang` links | 0 |
| conflict markers left in the tree | 0 |

## Never commit a credential

This repository is **public**. Tokens, service-account JSON, `.env` files and

minutes — that is why push failures usually mean "get a fresh token", not
"fix the remote URL". Use the secret manager, and read `GITHUB_TOKEN` from the

## Repo hygiene — the repository must not collect garbage

The repository reached 1.45 GB once and was reset on 26 Nov 2026. This section
is what keeps it from happening again. The rule the owner gave: **as commits
land, the size may grow with the content, but junk must never accumulate.**

### Budget

| measure | stay under | checked by |
|---|---|---|
| pack size (what GitHub stores) | 150 MB | `node tools/repo-health.js` |
| single tracked file | 10 MB | pre-commit hook |
| files touched by one commit | 1,000 | `node tools/repo-health.js` |

### Where the 1.45 GB came from

Not from content. From 442 commits that each snapshotted roughly 380 MB of
HTML, because several passes rewrote the whole tree at once: the inline-style
to class migration, the Assamese translation, the schema cleanup, and the
asset restamp that touches 3,211 pages every time `css/` or `js/` changes.

That last one is the sneaky one. Changing one rule in `css/style.css` changes
its hash, the hash lives in a `?v=` query string on every page, so the commit
rewrites 3,211 files and writes 40-60 MB of new blobs. Do that twenty times and
the repository is a gigabyte, with the same 611 MB of content.

### The four layers

1. **Repository settings** (already on): squash-only merges, and the head
   branch is deleted automatically on merge. One PR therefore adds exactly one
   commit and leaves no branch behind. A branch left open after a squash merge
   is pure garbage, because it pins its own copy of every commit.

2. **Pre-commit gate**: `.githooks/pre-commit`. Blocks generated artifacts
   (`*.csv`, `*.bundle`, `*.zip`, `*.log`), build output (`node_modules/`,
   `_preview/`, `dist/`), any staged file over 10 MB, and any staged HTML, CSS,
   JS, JSON or Markdown file that still has conflict markers. Enable it once
   per clone:

   ```bash
   git config core.hooksPath .githooks
   ```

   Bypass only deliberately, with `git commit --no-verify`, and say why.

3. **Health report**: `node tools/repo-health.js`. Prints pack size, commit
   count, the largest tracked files and the largest objects in history, and
   exits 1 when a budget is broken. Run it before a push and after any
   site-wide pass.

4. **Reset when the budget breaks** (was needed once, may be needed again in
   a year). The procedure that worked, in order:

   ```bash
   git bundle create ../history-backup.bundle --all     # never skip this
   git checkout --orphan clean-history
   git add -A && git commit -m "Site as of <date>"
   git push --force origin clean-history:main
   # delete every other branch, then:
   node tools/repo-health.js                             # packs back to ~80 MB
   ```

   Two things to know before doing it:
   - `main` is force-pushed, so announce it. Old SHAs stop existing.
   - The old objects are **not** freed automatically, because closed pull
     requests pin them through the read-only `refs/pull/*/head` references.
     The size only drops after GitHub runs housekeeping (support ticket), or
     after the repository is recreated from the clean tree. That is exactly
     why the repository was recreated on 26 Nov 2026.

### Rules that keep it small without a reset

- **Batch site-wide passes.** One commit that restyles 3,211 pages costs the
  same as one that restyles 5, but doing it in five commits costs five times.
- **Never commit generated output.** Audit CSV, keyword maps, bundles, backup
  archives, screenshots of your own pages: they are in `.gitignore` for a
  reason.
- **No duplicate banks.** `tools/legacy-banks/` is the old copy; edit the live
  bank under `data/`, not both.
- **Images stay small.** Compress before adding; a 2 MB hero image costs 2 MB
  in every clone, forever.
- **Close PRs by merging, not abandoning.** An abandoned branch keeps its
  commits alive for as long as the branch exists.

### Answer options: four distinct, or none

Every question needs four **different** options. If you generate questions,
never pad a list by repeating the correct answer with a label such as
`(incorrect)`: a reader who picks that letter is not wrong and still loses the
mark, and it is the kind of filler that gets an AdSense review rejected.

`tools/fix-duplicate-options.js` keeps banks honest:

- `node tools/fix-duplicate-options.js` — dry run: lists every question whose
  options repeat, and proposes a replacement from a question with the same
  template, so a river question gets a river.
- `--apply` — writes the bank, the matching page and any source module.
- `--prune` — removes questions that cannot be repaired (fully padded options,
  or options that just echo the question).
- `--drop-padded` — removes a single dead option, leaving a valid three-choice
  question.
- `--sync-ordered` — rebuilds option text and the answer line in the page from
  the bank, for pages that drifted.

After any content change, run the whole tool in dry-run and confirm it reports
zero.

### Before an AdSense review, audit thin pages

`python3 tools/content-audit.py` prints the signals a review reacts to: thin
pages, stems repeated inside or across banks, template families, and
explanations reused word for word.

Thin pages are pages a reader learns nothing from, and they drag down the
whole site. Keep a page indexable only if it carries real practice or real
notes. `assam-police-combo` is the current example: 105 pages holding 85
questions between them, so the section is `noindex, follow` and out of the
sitemap until it has content worth reading. `node tools/sync-sitemap-alts.js`
reads the `noindex` flag and keeps the map honest.

### Repeated explanations

`python3 tools/diversify-explanations.py` rewrites the one-line explanations
that a whole bank shares word for word, keeping the rule and adding the detail
that belongs to the question: the statement, the conclusions, the sentence, the
tag. It only writes when the added detail is copied out of the item, so a
question it cannot ground is left alone. Run it after any rebuild that
regenerates explanations.

Two of those questions can be worked out from the drawing itself, and the tool
does it rather than paraphrase the rule:

- cube nets: `b_cube_net` reads the numbers and their cells out of the net,
  folds it cell by cell and quotes the strip that puts the pair opposite each
  other. `python3 tools/fix-cube-nets.py` redraws nets that were drawn with too
  few faces; it only rewrites a figure when the fold then agrees with the key.
- paper folding: `paper_fold` reads the creases and the punch, mirrors the hole
  across every crease and picks the option that matches. It speaks only when
  exactly one option matches and that option is the key.

Both leave the figure, the options and the key untouched unless the fold itself
disagrees with them; those items are reported instead of edited.

Some of those questions draw the sheet as a cell grid and state the fold in the
stem ("vertical centre line", "from left to right", "folded twice in half").
There the drawn grid lines are cell borders, not creases: the fold is the named
centre line, and the drawing is folded only across that. Matching the options by
the order of their hole positions rather than their exact coordinates covers the
questions whose option figures use a finer lattice than the question figure.

The assam-police paper bank draws the same idea as steps: one panel per fold,
with the crease dotted and an orange arrow showing which part is laid over
which, then a last panel with the punch as a red dot. Each fold is read as a
crease position plus a kept side, and the punch is carried back through the
folds in reverse, so the holes come out where the opening sheet would put them.
A slanting crease is handled as one reflection across that line.

Grid-completion figures come in three drawing styles: cells drawn as rounded rects
with the shape inside (rrb), cells whose shape sits in a translated group and whose
option is a bare shape (assam-police), and shaded tile grids. The cell figure is
described from what is drawn - square, ringed circle, crossing lines, solid dot,
shaded tile - and the missing cell is predicted from the repeat along its row or
column, or from the whole step that carries one cell onto another. The explanation
names both cells, and is written only when exactly one option matches.

The adre banks draw one sheet with a dashed crease and either a white cut piece or a
white punched ring, and the options show the sheet open. The crease may be
vertical, horizontal or slanting, so every crease is kept as a line and the cut
(reflected as point sets, rings as centres) is carried out across each line until
no new copy appears; the answer is the option whose pieces match that set. Where
the options carry numerals instead of drawings, the same unfolding gives the count.

Three repairs run beside them, all in the dhs-dme paper bank:
`tools/fix-option-figures.py` replaces option figures that held a Python tuple
(`('1', '১', '')`) with the numeral itself, and `tools/add-paper-figures.py`
draws the folded sheet for the counting questions that never had one, writing
only when folding the drawing gives the count the key states;
`tools/fix-paper-grid-figures.py` moves a punch that the drawing placed on the
fold line, or split across two halves, into the quarter the answer itself shows,
and keeps the redrawn sheet only when folding it reproduces that answer.
